Ferry documentation

Ferry is a self-hostable checkout. Merchants receive an exact amount of one asset at one address. Buyers pay with any asset in the live NEAR Intents list, from that asset's own chain.

On this page: Quickstart · Payment flow · amountIn and minAmountIn · Replacing quotes · When an order is paid · Reconciliation inbox · Hosting · Assets & chains · Embed · NEAR AI · HTTP API · Security · Limits

Quickstart

node --version            # needs 22.13 or newer (uses built-in node:sqlite)
npm run merchant:create -- "My Store"   # prints an access key once
npm start                 # http://127.0.0.1:4317 (SQLite at data/ferry.db)
npm test                  # SQLite + Postgres (PGlite) suites
# server-side secrets / settings
NEAR_AI_API_KEY=...       # enables the setup assistant
NEAR_AI_MODEL=Qwen/Qwen3.8-27B   # default; reasoning disabled per NEAR AI docs
ONECLICK_JWT=...          # optional 1Click partner JWT; lowers fees
DATABASE_URL=postgres://… # Postgres (e.g. Neon pooled URL); required in production

Sign in at /dashboard with the access key. Set your payout asset and address, add products, then share /p/<product-id> links or embed buttons.

Payment flow

  1. Order. Opening a product link and pressing pay creates an order on the server. The order fixes the item, the amount in base units, the payout asset and the payout address. It gets a secret checkout URL (/c/chk_…) that's separate from its internal order ID.
  2. Quote. The buyer chooses an asset and enters a refund address. Ferry sends POST /v0/quote to 1Click with swapType: EXACT_OUTPUT, amount set to the order amount, depositType: ORIGIN_CHAIN and recipientType: DESTINATION_CHAIN. It checks that the response repeats the same amount, recipient and destination before storing the quote and its 1Click signature.
  3. Deposit. The page shows amountIn (the suggested input, with slippage already included) and minAmountIn (the minimum), the address with a copy button and a QR code generated on Ferry's own server, any memo, and a countdown. The provider looks the deposit up by depositAddress and, when present, depositMemo.
  4. Settlement. Market makers fill the intent and deliver exactly the order amount to the merchant. Ferry polls GET /v0/status in the background and whenever the checkout page is open.

amountIn, minAmountIn, and the deadline

For EXACT_OUTPUT, 1Click fixes the destination amount and applies slippage to the input. amountIn is the proposed input with the slippage tolerance baked in. minAmountIn is the minimum input required. amountIn is higher than minAmountIn by about the slippage tolerance. That gap is a buffer, not a shortfall and not price degradation. Ferry stores both, as integer base units, with the rest of the quote and its signature.

A reported depositedAmount is compared with minAmountIn only when both are present as integer base units. If depositedAmount is missing, the shortfall is UNKNOWN. Ferry does not subtract from amountIn to invent one, and it does not treat a missing amountOut, refundedAmount, or refundReason as zero. A deposit that is at least minAmountIn and still below amountIn is inside the buffer.

The destination amount is conditional on a successful eligible execution. It is not a fiat amount and not an unconditional guarantee. 1Click's own description says input above what the swap needs is refunded to refundTo after the swap completes, and a deposit below minAmountIn is refunded by the deadline. The quote field deadline is also described as the time the deposit address becomes inactive and funds may be lost. Ferry shows both facts and does not promise that a late deposit will come back.

Changing token, double payments and expiry

An order holds one active set of deposit instructions at a time. Only one quote request per order runs at a time, enforced with a lock in the database, and each order allows at most six quotes. To switch tokens while instructions are still active, the buyer has to confirm they haven't sent anything to the current address. The old address stays valid at 1Click until its own deadline, so Ferry keeps checking it. If two deposits settle, the order stays paid and is flagged Extra payment: that is a merchant refund after settlement, which Ferry does not send. The provider status REFUNDED is a different event, a swap refund from 1Click.

Ferry's invoice expiry is local. 1Click has no EXPIRED status. A deposit that is still PENDING_DEPOSIT, KNOWN_DEPOSIT_TX, INCOMPLETE_DEPOSIT, or PROCESSING stays visible after the local invoice time. KNOWN_DEPOSIT_TX means a deposit transaction has been seen. Seen is not settled.

When an order is marked paid

An order becomes paid only when every one of these is true:

  • 1Click reports SUCCESS for a deposit address Ferry issued for this order.
  • The status response's quote has the same deposit address, memo and signature as the stored quote.
  • The request it reports was EXACT_OUTPUT to the order's recipient and destination asset, for the order's exact amount, from the stored origin asset, with the stored refund address.
  • The reported amountIn and minAmountIn equal the amounts the buyer was shown.
  • Any settled amountOut that's reported is at least the order amount.

A SUCCESS that fails these checks puts the order into needs_review and doesn't mark it paid. Ferry has no endpoint that accepts a transaction hash or a client callback as proof of payment. Provider statuses Ferry understands are PENDING_DEPOSIT, KNOWN_DEPOSIT_TX, INCOMPLETE_DEPOSIT, PROCESSING, SUCCESS, REFUNDED, and FAILED. Each stored status keeps updatedAt and the status correlationId when the provider sent them, plus transaction hashes and explorer URLs. A missing updatedAt stays unknown.

Reconciliation inbox

The Orders tab is the merchant inbox. It sorts stored orders into paid, processing, needs attention, and open (no deposit in flight). Opening an order shows the quote evidence, a timeline of stored events, the freshness of the last provider read, and every unknown. The diagnosis is labelled deterministic rules. It does not change the order.

A failed or stale refresh is shown as a failure. Ferry does not describe the last stored status as freshly confirmed. Resolution notes are text the merchant saves. Saving one does not change price, payout, or payment state. The CSV export is the same evidence, one row per quote. Cells that start with =, +, -, or @ are prefixed so a spreadsheet does not treat an item name as a formula. Missing provider amounts are the word UNKNOWN.

The optional explanation asks NEAR AI only after Ferry has tried to refresh provider status. When no quote is stored, that refresh does not call the provider and is not a failure. The fact sheet includes the display amount and the base units separately. The reply must match a strict schema, cite only evidence ids Ferry supplied, and must not state an amount, a failed refresh, or a quote deadline the facts do not support. A reply that fails those checks is stored as invalid, without the rejected sentences, and is not shown as advice. Explanations stored before the claim check are left in the database and are not rendered as validated. The model has no tool, no refund, and no way to mark an order paid. If NEAR_AI_API_KEY is unset, or the provider rejects it, the inbox still works and the health status stays unset, unverified, or auth_failed. A key that has not completed a successful call is not reported as connected. A rejected explanation is not a successful narrative, and Ferry does not replace it with rules text labelled as the model's answer. The rules diagnosis stays separate.

GET /api/simulated-cases returns fixed demonstration cases run through the same rules. They are marked SIMULATED, they are not inserted into the order table, and they are not counted as paid, processing, or attention. No mainnet settlement has been verified.

Ferry is not a spending or budget product. It does not score purchases or move money. Partial, late, and overpaid cases are shown because swap settlement is that complicated: a seen transaction is not final, a provider refund is not a merchant refund, and review or copy is the only action on the page. This is not a claim that buyers asked for an AI refund desk.

Assets & chains

Ferry reads GET /v0/tokens and caches the list for 5 minutes, keeping a persisted fallback copy. Ferry supports exactly what that list contains at the moment, and nothing more. Payout chains are limited to NEAR, EVM chains and Solana, because Ferry can only validate those address formats. Refund addresses on other chains get a structural check, and 1Click validates them when quoting. If you pay out to a NEAR account, it must be registered for the token's storage, or delivery can fail.

NEAR Intents has no testnet. Every non-dry quote is a real mainnet deposit address. To test, use a separate account and small amounts. 1Click can reject amounts that are too small, so don't assume a minimum.

Embed

<script src="https://YOUR-FERRY-HOST/embed.js" defer></script>
<div data-ferry-product="prd_…" data-ferry-label="Pay with crypto"></div>

The script only renders a link to Ferry's hosted product page. No payment code or secrets run on your site.

NEAR AI setup assistant

When NEAR_AI_API_KEY is set, Ferry sends the merchant's brief to NEAR AI Cloud (POST https://cloud-api.near.ai/v1/chat/completions, Bearer auth). It uses response_format: json_schema (strict) and the model in NEAR_AI_MODEL, by default Qwen/Qwen3.8-27B, which NEAR AI lists with tools and structured_outputs. Reasoning is turned off with chat_template_kwargs.enable_thinking: false, as NEAR AI's reasoning-models guide describes, so the token budget (NEAR_AI_MAX_TOKENS, default 1500) goes to the JSON itself. A response cut off at the token limit is reported as an error and nothing is stored. In a live test on 2026-11-08 the draft used 739 prompt tokens and 419 completion tokens, with 0 reasoning tokens, and passed validation. The draft can include only these fields: tagline, about, button label, accent from a fixed palette, product names and descriptions, FAQ, and suggested asset IDs.

Ferry then runs its own deterministic validator. It rejects any extra or forbidden field (anything resembling a recipient, price, amount, address, payment status or transfer), any text that's too long or contains markup, and any asset ID that isn't in the live list. The merchant sees a diff and picks the fields to apply. Product copy becomes a product only after the merchant enters their own price. When no key is set, the assistant says so and stays off. Ferry never fabricates a draft or switches to another provider.

Security

  • Secrets (the 1Click JWT and the NEAR AI key) live only in server environment variables and never reach the browser.
  • Merchant access keys, session tokens and checkout secrets are stored only as SHA-256 hashes.
  • A strict Content-Security-Policy is applied, with no third-party scripts. Every page sets frame-ancestors 'none'.
  • State-changing requests must be same-origin, carry a JSON content type and stay under the body-size limit. Orders, quotes, sign-ins and AI calls are rate-limited.
  • Rate limits are stored in the database, so they apply across serverless instances. Upstream service URLs are set by the operator only, and must be https in production. Ferry never fetches a URL a user supplies.
  • Amounts are handled as BigInt base units. Decimals are parsed exactly and floats are never used.

Hosting (Vercel + Neon)

  1. Create a dedicated Neon project for Ferry (the free plan is enough). Run DATABASE_URL_UNPOOLED=… npm run db:migrate using the direct connection string.
  2. Import the repo into Vercel. vercel.json sends every route to api/index.js (Node.js, Fluid Compute) and bundles public/.
  3. Set these environment variables: DATABASE_URL (the pooled URL), PUBLIC_BASE_URL, CRON_SECRET, NEAR_AI_API_KEY, and optionally ONECLICK_JWT. Don't set FERRY_DEV; production refuses it.
  4. Create merchants from a trusted terminal: DATABASE_URL=… npm run merchant:create -- "Store".

Current limits

  • Outbound merchant webhooks aren't implemented yet. They'll need signed payloads, an allowlist of destinations to prevent SSRF, retries and idempotency. Until then, merchants check orders in the dashboard.
  • On Vercel's free Hobby plan, scheduled jobs run once a day, so status updates mostly come from open checkout pages and merchant refreshes; the daily sweep catches anything left over.
  • Merchant sign-in is by access key only; there are no user accounts yet.
